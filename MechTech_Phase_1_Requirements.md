## 1. Project Overview

### 1.1 Project title

**MechTech: An Intelligent Equipment Monitoring and Fault Diagnosis
System Using 3D Digital Twins, Machine Learning, and Repair Knowledge
Graphs**

### 1.2 Short description

MechTech is a software-first predictive-maintenance and
equipment-monitoring platform. Its initial prototype focuses on one
piece of equipment: an **electric motor**.

The system receives temperature and vibration readings, initially
generated by a local Python sensor simulator. It visualizes the
equipment and its operating condition through a realistic interactive 3D
motor model, monitors sensor trends, detects unusual operating
behaviour, predicts possible fault categories using machine learning,
and connects symptoms and possible faults to diagnostic and repair
knowledge.

MechTech is intended to help operators and technicians monitor equipment
and investigate possible problems. It is a decision-support tool, not an
autonomous safety system and not a substitute for qualified mechanical
inspection.

### 1.3 Tagline

**Detect. Diagnose. Maintain.**

### 1.4 Project category

-   Full-stack web application
-   Industrial IoT / equipment monitoring
-   Predictive maintenance
-   Applied machine learning
-   3D digital-twin-style visualization
-   Repair and maintenance knowledge management

### 1.5 Core project idea

Combine five capabilities in one platform:

1.  **Sensor monitoring:** collect and display timestamped motor
    readings.
2.  **Machine learning:** identify unusual patterns and estimate
    possible fault categories.
3.  **3D visualization:** show a realistic interactive representation of
    the motor and its components.
4.  **Repair knowledge:** connect components, symptoms, possible faults,
    diagnostic steps and repair procedures.
5.  **Maintenance management:** record alerts, inspections, repairs and
    outcomes.

## 2. Problem Statement

Equipment operators and maintenance technicians need to understand the
condition of machines and respond when operating behaviour changes.
Manual inspections and simple fixed-threshold alerts can provide useful
information, but they may not reveal more complex patterns or connect an
observed symptom to relevant diagnostic and repair information.

MechTech proposes an integrated platform that monitors selected sensor
readings, detects abnormal behaviour, estimates possible fault
categories, visualizes the equipment and relevant components, and
provides structured maintenance knowledge.

The first version will use a simulated electric-motor environment so
that the complete software workflow can be developed and tested without
purchasing hardware.

------------------------------------------------------------------------

## 3. Objectives

The main objective is to design and develop a local-first intelligent
equipment-monitoring prototype for an electric motor.

Specific objectives:

-   Register and manage motor equipment.
-   Generate or receive timestamped temperature and vibration readings.
-   Display current readings and historical trends.
-   Establish a baseline of normal simulated operating behaviour.
-   Detect unusual readings or patterns.
-   Classify selected simulated fault categories using a supervised ML
    model.
-   Display model outputs with confidence/probability information where
    appropriate.
-   Provide a realistic interactive 3D motor visualization.
-   Map sensor indicators and possible fault highlights to relevant
    motor components.
-   Maintain a structured knowledge graph of components, symptoms,
    faults, diagnostic steps and repairs.
-   Record maintenance activities and repair outcomes.
-   Evaluate ML performance using held-out labelled test data.
-   Keep the architecture extensible so physical sensors and additional
    equipment types can be added later.

-   Explore the 3D motor and highlighted components.

2.  Cooling fins
3.  Shaft
4.  Bearings

-   Show relevant sensor readings in a component information panel.
-   Show sensor-position markers.
-   Highlight a component when an alert or prediction is associated with

-   Provide a reset-camera view.
-   Maintain usable performance on a typical Windows 11 laptop.

The initial model is a visualization, not a mechanically accurate
physics simulation.

## 8. Sensor and Data Requirements

### 8.1 Initial sensor channels

The first prototype uses two sensor channels:

  -----------------------------------------------------------------------
  Channel                 Meaning                 Initial unit
  ----------------------- ----------------------- -----------------------
  Temperature             Motor or selected       °C
                          component temperature   

  Vibration               A simplified vibration  Use a clearly
                          indicator               documented unit/scale
  -----------------------------------------------------------------------

Important: vibration must have a defined representation. If the
simulator produces a simplified vibration magnitude or arbitrary
normalized value, the interface and documentation must label it
accurately. Do not label a synthetic arbitrary value as a calibrated
industrial measurement such as mm/s RMS unless the data generation and
unit definition actually support that claim.

### 8.2 Suggested reading structure

Each reading should contain at least:

-   Reading ID
-   Equipment ID
-   Timestamp (UTC stored internally; display in local time)
-   Temperature value
-   Vibration value
-   Source identifier (for example, `simulator`)
-   Data-quality/status information where needed

A future hardware source should be able to send the same normalized
reading structure.

### 8.3 Simulator operating scenarios

The Python simulator should be able to generate reproducible scenarios:

1.  **Normal operation:** readings fluctuate within a configured normal
    simulated range.
2.  **Increased vibration:** vibration rises while temperature may
    remain near normal.
3.  **Overheating:** temperature rises while vibration may remain near
    normal.
4.  **Combined abnormality:** both channels show abnormal behaviour.
5.  **Sensor disconnection:** one or more readings stop arriving.
6.  **Noisy sensor:** readings contain increased noise or occasional
    spikes.
7.  **Return to normal:** values return to the configured normal
    pattern.

The simulator should support:

-   Selecting a scenario.
-   Configuring a scenario duration or switching scenarios.
-   Configuring the generation interval.
-   Setting a random seed for repeatable experiments.
-   Marking generated scenario labels for evaluation.
-   Clearly distinguishing simulated data from physical sensor data.

All numerical thresholds and ranges must be configurable and described
as **prototype simulation settings**, not universal motor safety limits.

### 8.4 Data-quality behaviour

The backend should:

-   Validate types, ranges and required fields.
-   Reject malformed records with a useful error.
-   Avoid silently converting invalid data into plausible measurements.
-   Detect stale readings or a missing-data interval.
-   Preserve timestamps and source metadata.
-   Handle duplicate or out-of-order readings according to a documented
    policy.
-   Make sensor disconnection visible as a data-quality/connection
    status, not automatically classify it as a mechanical fault.

## 9. Machine Learning Requirements

Machine learning is a central project feature, but it must be developed
incrementally and evaluated honestly.

### 9.1 ML objectives

The ML layer should:

-   Learn or use a baseline for normal simulated behaviour.
-   Detect unusual readings or patterns.
-   Classify supported simulated fault scenarios.
-   Return understandable output for the dashboard.
-   Preserve model version and prediction timestamp.
-   Be testable independently of the frontend.

### 9.2 Initial anomaly detection

**Suggested first model: Isolation Forest**

Purpose: - Learn the distribution of normal simulated sensor
behaviour. - Flag unusual observations or feature windows. - Provide an
anomaly score or normal/anomalous result.

A simple statistical baseline or configurable threshold method should
also be implemented as a baseline for comparison. Do not assume
Isolation Forest will always be better.

### 9.3 Initial fault classification

**Suggested first classifier: Random Forest**

Initial simulated classes:

-   `normal`
-   `excessive_vibration`
-   `overheating`
-   `bearing_related_abnormality`
-   `combined_abnormality`

The dataset must include labels generated by the simulator. Features may
include: - Temperature - Vibration - Rolling mean - Rolling standard
deviation - Minimum and maximum within a window - Rate of change - Other
clearly documented signal features

Feature engineering should be simple and explainable initially. Avoid
adding complex algorithms before the data pipeline and evaluation are
reliable.

### 9.4 Prediction output

A prediction record should include:

-   Equipment ID
-   Prediction timestamp
-   Model name and version
-   Predicted class
-   Confidence/probability information, if supported and calibrated
    appropriately
-   Anomaly score, where relevant
-   Input window or evidence reference
-   Human review status (for example, unreviewed, confirmed, rejected,
    inconclusive)

Model confidence is not the same as the probability that a real machine
has a fault. The UI must avoid implying otherwise.

### 9.5 Model evaluation

Use a held-out test dataset that is not used for training or model
selection.

Report relevant metrics: - Accuracy - Precision - Recall - F1-score -
Confusion matrix - False-positive rate

For anomaly detection, explain how labels and thresholds are defined and
report appropriate detection metrics.

Use repeatable train/test splitting or time-aware splitting where
appropriate to reduce data leakage. Keep scenarios or time segments
separated where needed so near-duplicate simulated samples do not make
the evaluation misleading.

**Critical limitation:** strong performance on synthetic data
demonstrates performance on the simulator's patterns only. It does not
establish accuracy on real industrial motors. Any future real-world
validation must use appropriately collected, labelled physical data.

### 9.6 Explainability

Initially show direct evidence such as: - Which sensor channel
changed. - How the current reading compares with the configured
baseline. - Which recent time window was considered. - Which features
contributed to a rule or model output, where available.

SHAP may be considered later. It is not a prerequisite for the first
working ML pipeline.

### 9.7 Predictive maintenance boundary

The initial version may provide: - Anomaly detection. - Possible
fault-category classification. - Trend monitoring. - Suggested
inspection/maintenance attention.

It must **not** claim: - Guaranteed diagnosis. - Guaranteed failure
prediction. - Exact remaining useful life. - Exact date/time of
failure. - Safety certification. - Universal thresholds applicable to
all motors.

## 10. Repair Knowledge Graph Requirements

### 10.1 Purpose

The knowledge graph connects information that would otherwise be stored
as disconnected lists. It helps a technician navigate from an observed
symptom to possible causes, diagnostic checks and repair knowledge.

### 10.2 Initial node types

-   Equipment
-   Component
-   Sensor
-   Symptom
-   Fault
-   DiagnosticStep
-   RepairAction
-   Part
-   MaintenanceRecord

### 10.3 Example relationship types

-   `HAS_COMPONENT`
-   `HAS_SENSOR`
-   `MONITORS`
-   `MAY_CAUSE`
-   `INDICATES`
-   `AFFECTS`
-   `CHECK_WITH`
-   `MAY_BE_RESOLVED_BY`
-   `REQUIRES_PART`
-   `RECORDED_IN`

### 10.4 Example knowledge flow

A simplified example:

`Vibration increase` → may indicate → `Bearing-related abnormality` →
affects → `Bearing` → inspect using → `Bearing inspection procedure` →
may be addressed by → `Bearing maintenance/replacement`

These are example knowledge relationships for the prototype, not
authoritative engineering diagnoses. The graph should allow multiple
possible causes for the same symptom.

### 10.5 Initial implementation

Use **NetworkX** in Python for the initial graph. Persist the graph's
source data in a structured, maintainable format or database tables so
the graph can be reconstructed. A dedicated graph database is not
required in Phase 1.

## 11. Alerts and Severity

The system should store alert events with:

-   Alert ID
-   Equipment ID
-   Event timestamp
-   Event type
-   Severity
-   Related sensor channel(s)
-   Relevant reading or time-window reference
-   Anomaly score or model output where applicable
-   Description
-   Review status
-   Technician notes, if any

Suggested prototype severity levels:

-   `info`
-   `warning`
-   `critical`

Severity mapping must be configurable and documented. A `critical` label
in the prototype is a software alert classification, not a certified
machine-safety determination.

Alerts should distinguish: - Abnormal sensor behaviour - Possible fault
prediction - Sensor/data connection issue - Maintenance reminder or
inspection record

## 14. Non-Functional Requirements

### 14.1 Performance

-   Dashboard updates should feel responsive during local simulation.
-   Charts should handle the expected prototype data volume.
-   3D interactions should remain usable on a typical Windows 11
    development laptop.
-   Avoid unnecessary re-rendering and unbounded in-memory data growth.

### 14.2 Reliability

-   Handle backend errors and simulator disconnections gracefully.
-   Display stale-data status when new readings stop arriving.
-   Do not present stale readings as live values.
-   Persist important records in the database.
-   Log errors sufficiently for debugging.

### 14.3 Security

-   Hash passwords using a suitable password-hashing algorithm.
-   Validate and authorize API requests on the backend.
-   Enforce role permissions server-side.
-   Keep secrets in environment variables; never commit real secrets.
-   Apply safe CORS configuration.
-   Avoid exposing sensitive stack traces to normal users.
-   Do not store API keys or tokens in frontend source code.

### 14.4 Usability and accessibility

-   Use clear labels, units and timestamps.
-   Provide loading, empty, error and disconnected states.
-   Keep navigation consistent.
-   Ensure status is not represented by colour alone.
-   Provide understandable explanations for ML output.

### 14.5 Maintainability

-   Separate frontend, backend, simulator, ML, graph and database
    responsibilities.
-   Use typed API schemas and documented data contracts.
-   Keep configuration outside source code.
-   Add tests for core functionality.
-   Use Git for version control.

### 14.6 Portability

-   The project should run locally on Windows 11.
-   Setup instructions should explain required software and commands.
-   Avoid requiring paid cloud infrastructure.

## 16. High-Level System Architecture

### 16.1 Logical flow

``` text
                 LOCAL PYTHON SENSOR SIMULATOR
                    (future: ESP32 / MQTT)
                              |
                              v
                     FASTAPI BACKEND
                 Validation / Business Logic
                              |
              +---------------+----------------+
              |               |                |
              v               v                v
        SQLITE DATABASE   ML PIPELINE     NETWORKX GRAPH
        Users             Features        Components
        Equipment         Anomaly         Symptoms
        Readings          Detection       Faults
        Alerts            Classification  Diagnostics
        Predictions       Model Output    Repairs
        Maintenance
              |               |                |
              +---------------+----------------+
                              |
                     REST API / WEBSOCKETS
                              |
                              v
                    REACT + TYPESCRIPT UI
                              |
             +----------------+----------------+
             |                |                |
             v                v                v
       MONITORING        3D MOTOR VIEW     DIAGNOSIS /
       DASHBOARD         (R3F / THREE)     MAINTENANCE UI
```

### 16.2 Architectural principles

-   The simulator and future hardware must use the same normalized
    sensor-data contract.
-   The frontend must not directly access the database.
-   ML inference should be encapsulated behind backend services.
-   The knowledge graph should be accessed through backend services/API
    routes.
-   Prediction, anomaly and alert records should be persisted where
    appropriate.
-   3D visualization consumes application data; it does not
    independently determine faults.
-   The system must remain useful when the optional 3D view or ML
    service is temporarily unavailable.

## 19. Acceptance Criteria and Demonstration Scenarios

The prototype should be demonstrable from beginning to end.

### AC-01: Equipment registration

An authorized administrator can register an electric motor and see it in
the equipment list.

### AC-02: Normal simulated operation

The simulator generates timestamped temperature and vibration data. The
backend validates and stores readings. The dashboard displays the latest
values and trends.

### AC-03: Abnormal vibration scenario

When the simulator switches to increased vibration, the dashboard
reflects the changed readings and the anomaly detector can identify the
configured abnormal pattern.

### AC-04: Overheating scenario

When the simulator switches to overheating, temperature trends change
and the system can produce an anomaly event or relevant classification
output.

### AC-05: Combined abnormality

The system handles a scenario in which both channels change abnormally.

### AC-06: Sensor disconnection

When readings stop, the dashboard indicates stale data or disconnection.
It must not mislabel missing data as a mechanical fault.

### AC-07: ML prediction

For supported labelled simulated scenarios, the classifier returns a
predicted class and appropriate supporting information. Its performance
is evaluated on held-out data.

### AC-08: 3D visualization

A user can rotate and zoom the realistic motor model, select components
and view component information.

### AC-09: Fault/component highlighting

When an event is associated with a component, the 3D view can highlight
that component and show the related event. The highlight is presented as
an investigation aid, not proof of damage.

### AC-10: Knowledge graph

A user can navigate from a symptom to possible faults, affected
components, diagnostic checks and repair actions.

### AC-11: Maintenance record

A technician can create a maintenance record and later retrieve it.

### AC-12: Role security

Users cannot perform protected operations outside their assigned
permissions, even if they manually call the API.

## 21. OpenAI and OmniRoute Development-Assistant Context

The project may be developed with the help of coding assistants using
OpenAI models and OmniRoute. These tools are part of the **development
workflow**, not mandatory runtime dependencies of MechTech.

Important implementation boundaries:

1.  Do not assume that an OpenAI API key is available to the deployed
    MechTech application.
2.  Do not hard-code a model provider, API endpoint, API key or
    OmniRoute configuration into the core application.
3.  The core anomaly detection and fault classification must run locally
    using the Python ML stack.
4.  Do not require an LLM to generate sensor data, execute predictions
    or operate the dashboard.
5.  An optional LLM-assisted explanation feature may be considered in a
    later phase, behind a provider-independent service interface.
6.  If an optional LLM feature is implemented, it must handle missing
    configuration, API errors, rate limits and costs gracefully.
7.  Never expose API keys in frontend code, Git repositories, logs or
    screenshots.
8.  Treat all generated code as needing review, testing and security
    checks.

The coding assistant should use this document as project context, but
should not attempt to implement the entire application in one step. Work
phase-by-phase and keep the implementation aligned with the
requirements.

## 25. Final Project Summary

**MechTech** is a zero-budget, local-first intelligent electric-motor
monitoring and fault-investigation platform. It combines simulated
sensor data, real-time monitoring, machine-learning-based anomaly
detection and fault classification, a realistic interactive 3D motor
visualization, a repair knowledge graph, and maintenance-history
management.

The initial prototype uses React, TypeScript, FastAPI, SQLite, Python,
Scikit-learn, NetworkX and React Three Fiber. It begins with simulated
temperature and vibration data and is designed so physical sensors can
be integrated later through the same data contract.

Its purpose is to provide useful monitoring and maintenance decision
support while clearly communicating uncertainty and the limitations of
synthetic-data-based predictions.

**MechTech --- Detect. Diagnose. Maintain.**
